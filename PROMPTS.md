# Промпты, использованные при выполнении задания

## 1. Создание проекта

> Описание задачи: веб-приложение для хранения PDF и DOCX с ограниченным сроком хранения… делаем ограничение на тип данных через Form Request… 2 отдельные страницы для загрузки и для crud операций… сервис для отправки уведомлений нужно сделать через инверсию зависимостей… делай все развертывание через dockerfile и docker compose

**Результат:** проект на Laravel 12:

- **Загрузка** (`/upload`): асинхронная, на jQuery, с перетаскиванием файлов, загрузкой нескольких файлов сразу и прогресс-баром для каждого.
- **Управление файлами** (`/files`): список с пагинацией, обратный отсчёт до удаления, скачивание, удаление через AJAX с подтверждением.
- **Валидация** в Form Request `StoreFileRequest`: тип файла проверяется по содержимому (`mimes`) и по расширению (`extensions`), размер ограничен 10 МБ.
- **Хранение:** записи о файлах лежат в MySQL (таблица `stored_files`).
- **Автоудаление:** команда `files:purge-expired`, планировщик запускает её каждую минуту. Файлы удаляются через 24 часа.
- **Уведомления через инверсию зависимостей:** интерфейсы `Notifier` и `NotificationChannel`, классы `MultiChannelNotifier` и `EmailChannel`. Пример расширения — `TelegramChannel`, включается через `NOTIFICATION_CHANNELS` без правки основного кода.
- **RabbitMQ:** `EmailChannel` кладёт сообщение в очередь, отдельный worker (`notifications:consume-email`) читает его и отправляет письмо в Mailpit. Уведомление уходит и при ручном удалении, и при автоматическом.
- **Docker:** `Dockerfile` и `docker-compose.yml` с контейнерами app, nginx, scheduler, worker, mysql, rabbitmq, mailpit. Плюс тесты на загрузку и удаление и README.

## 2. Обновление списка после автоудаления

> не удаляется по истечению времени… счётчик обнулился и на этом пока всё

**Причина:** на сервере удаление работало: запись пропадала из БД, письмо уходило. Но страница после окончания отсчёта показывала «удаляется…» и больше ничего не делала.

**Результат:** в `public/js/files.js` добавлена проверка: пока на странице есть просроченные файлы, раз в 5 секунд она сверяется с сервером. Удалённые строки исчезают, появляется уведомление.

## 4. 502 после пересборки

> почини nginx чтобы не было 502 после пересборки

**Причина:** nginx узнавал IP контейнера `app` один раз при старте. Пересобранный `app` получал новый адрес, а nginx продолжал обращаться к старому, поэтому сайт отдавал 502.

**Результат:** в `docker/nginx/default.conf` добавлен DNS-резолвер Docker (`resolver 127.0.0.11 valid=10s`), а адрес PHP вынесен в переменную `$php_upstream`. Теперь nginx заново узнаёт IP по имени `app`. Проверено: `app` пересоздан с другим IP, сайт сразу ответил 200, nginx при этом не перезапускался.

## 5. Ревью проекта

> как думаешь, есть ли ещё что-то поправить в этом тестовом или всё сделано хорошо и тянет на уровень middle?

**Результат:** разбор проекта. Сильные стороны: инверсия зависимостей в уведомлениях, атомарное удаление без дублей писем, проверка типа по содержимому файла, healthchecks в Docker, тесты. Найдено, что стоит исправить:

- проект не в git;
- `composer.json` требует PHP `^8.2`, а `composer.lock` требует 8.4;
- worker теряет письма при временном сбое SMTP: нет повторов и dead-letter очереди;
- при пустом `APP_KEY` каждый контейнер генерирует свой временный ключ;
- просроченный файл можно скачать, пока его не удалил планировщик;
- нет ограничения длины имени файла: длинное имя давало 500 вместо ошибки валидации.

## 6. Исправления по ревью

> давай сделаем пункты 2-4 и так же добавим правки для просроченного файла и ограничения на длину имени

**Результат:**

- **Версия PHP:** в `composer.json` теперь `"php": "^8.4"`, хеш в `composer.lock` обновлён.
- **Повторы в RabbitMQ:**
  - если письмо отправить не удалось, сообщение уходит в `notifications.email.retry` и через `RABBITMQ_RETRY_DELAY_MS` (30 секунд) само возвращается в основную очередь;
  - после `RABBITMQ_RETRY_ATTEMPTS` (5) неудач оно попадает в `notifications.email.failed`, где его видно в интерфейсе RabbitMQ;
  - битый JSON и невалидные данные (`UnprocessableMessageException`) уходят в `.failed` сразу, без повторов;
  - добавлено 5 unit-тестов на эту логику. Проверено вживую: при остановленном SMTP сообщение ушло в `.retry`, после запуска Mailpit письмо пришло через 30 секунд.
- **Запуск с нуля:** `make up` и `make init` сами создают `.env` и `APP_KEY`, если их нет, существующий ключ не трогают. Полный сценарий проверен на чистой копии проекта: без `vendor` и `.env`, с новыми volumes.
- **Найдено по ходу: `make test` очищал рабочую базу.** Docker передаёт переменные из `.env` в `$_SERVER`, а `phpunit.xml` задавал тестовые значения через `<env>`, которые Laravel в этом случае не видит. Поэтому тесты в контейнере шли против настоящей MySQL, и `RefreshDatabase` стирал её таблицы. `phpunit.xml` переведён на `<server>`, теперь тесты в контейнере используют SQLite в памяти.
- **Просроченные файлы:** если срок вышел, а планировщик ещё не удалил файл, скачивание отвечает `410 Gone`, а кнопка скачивания в списке становится неактивной.
- **Длина имени:** имя длиннее 255 символов (по размеру колонки `original_name`) отклоняется валидацией с понятным сообщением на английском и русском.
- Из README убрана команда `php artisan tinker`: пакет tinker в проекте не установлен.
- Тесты: 25 из 25 проходят и локально, и в контейнере.
